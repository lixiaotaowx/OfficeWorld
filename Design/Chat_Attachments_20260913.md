# 聊天图片和文件

## 行为

- 公共聊天新增“＋ 图片 / 文件”，选取后显示文件名和大小，再点击发送文件。
- 单个文件 1 字节至 20 MB；一次发送一个，上传进度可见，失败保留选择以便重试。
  - **2026-09-21 更新（用户要求）**：上限提到 **2 GB**。`chat-files.mjs` 的 `MAX_FILE_SIZE` 与
    `src/chatAttachments.ts` 的 `MAX_CHAT_FILE_BYTES` 必须一致（服务端那份是硬门）。
    文件仍然**存在 VPS 上**（保留 7 天），所以上限变大等于磁盘占用变大——注意 `df -h /`（当时 22 GB 可用）。
    同时必须一起改的两处：下载的 `AbortSignal.timeout` 原来写死 60 秒（整条请求的期限，不是空闲期限），
    2 GB 永远下不完 → 改成随文件大小放大的 `downloadTimeoutMs`；超过 256 MB 的文件不再往 IndexedDB 里塞。
- PNG、JPEG、GIF、WebP 依文件字节识别预览，点击放大；其他格式提供下载。
- **下载走文件直传那条通道（2026-09-21 用户要求：「整理一下聊天框里面的文件下载，要带进度条，
  要软件内设置好下载位置，下载好了也还是有几个按钮 打开等 复用」）**：
  - 点「下载」→ `files.downloadAttachment()` → **落到设置里那个接收文件夹**（和拖到头像直传同一个目录，
    设置里改一处两边都变）；桌面客户端直接写盘，网页版只能是浏览器下载。
  - **进度条**：聊天那一条里有自己的细进度条（`.chat-file-bar`），同时还有任务栏那条系统进度条；
    两者和头像直传共用同一份被限流（200ms）的进度。
  - **完事的按钮**：「打开」「打开文件夹」；下载中可「取消」，失败变「重新下载」，并写明原因。
  - **行 id 就是附件 id**：聊天那一条和传输面板那一条是同一个记录，所以点两次不会下两遍。
  - 小附件（≤ `PREFETCH_MAX_BYTES` 4 MB）仍然后台预取 + 缓存，用来做图片预览和"离线也能看"；
    **大附件不再后台自动拉**——上限提到 2 GB 之后那会变成"打开一次聊天静默拉几个 GB"。
- 文件和消息在服务器保存最近 7 天，恰好 7 天仍可补收，超过后清理。
- 接收到的**小**附件自动写入当前账号的浏览器 IndexedDB，不由应用定时删除；大附件不写缓存
  （浏览器的配额经不起几个 GB），每次点下载重新拉。
- “已保存到本机”只在 Blob 写入事务完成后显示。失败显示接收错误并自动重试，也可手动重试。
- 本地存储属于当前浏览器和设备；清除网站数据、浏览器回收空间或换设备不会恢复已过期的服务器副本。

## 实现与边界

- chat-files.mjs：Socket.IO 每片 128 KB，低于现有 300 KB 消息上限，无需修改 nginx 上传限制。
- 根据服务器认证身份归属上传，不能指定他人姓名。单账号一个上传，全局最多 20 个同时上传。
- 分片确认、重试去重、顺序和总长度校验。末片 flush 后改名并持久化聊天消息，成功才广播。
- 文件存于 chat-data/files，以服务端 UUID 命名；不使用用户文件名作为路径。
- 中断上传立即清理；无进度超过 2 分钟清理，重启清理未完成和未引用的文件。
- 每分钟清理过期记录与文件。部署不复制或备份聊天数据，不延长保留时间。
- HTTP 下载必须有有效登录会话，统一 attachment/octet-stream、nosniff、no-store。
- HTML、SVG 不在网页中执行或预览；预览只使用经过字节识别的栅格图片 Blob URL。
- IndexedDB v1 无损升级到 v2，新增 files store；原有文字记录和历史游标保留。
- 历史游标保存与附件下载解耦；已收到的附件元数据在重启后重新排队补收。
